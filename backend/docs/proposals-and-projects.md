# Proposals, projects and roles

Part of the backend guide, see [CLAUDE.md](../CLAUDE.md).

- Proposals: a season is a season of the year plus a year (unique), a proposal belongs to one season and holds its participants (a "paw" is a `userName` with roles, embedded in the proposal). A person may join at most `MAX_PROPOSALS_PER_PERSON` (3) proposals per season, counted per season, one title counts once however many roles. `ProposalsService.setParticipation` enforces it: joins of one person are serialized in this process and the count is checked again after the push, so it also holds if the API ever runs twice. Changing roles of a title already joined never re-checks the cap, an empty role list withdraws.
- A closed season is read-only for members (join, change and withdraw answer 409). Admins can still edit its titles and participants, but cannot add a title or move one into it, and only a closed season can be deleted (with all its titles and paws). Moving a title between seasons does not re-check the cap. Admins can change or remove an existing paw (`PUT /proposals/:id/participants/:userName`), never create one for somebody else.
- Projects: a project belongs to the anime season (calendar quarter) of its `startDate`, which may be any day from 2000-01-01 (a typo like year `0025` would make `buildLayout` build a copy per season for thousands of seasons) to two years from today (`MAX_PLANNED_YEARS`, `shiftYears`; a typo like 2099 would make a tab of a far season). Dates are plain `YYYY-MM-DD` strings and "today" is the date in Kyiv (`todayInKyiv`). `GET /projects` returns the layout built by `buildLayout` in `projects/layout.ts`, nothing about seasons or debts is stored. A project is on the layout of every season from its start season to its end season (to the current one while it runs). In a season after its start it is a debt, unless it is finished and `isInTime`. Debt replaces the kind in the statistics, so `ongoing + old + debt = total`, while patron and order count on top. Only seasons with a project get a tab, plus the current one. **Planned projects:** a project whose start season has not come yet (`isPlannedDay`, a season after the current one) is `planned`: it is on the layout of its start season alone (a tab after the current one, only for seasons that hold one), marked `PROJECT_MARK.PLANNED`, never a debt, and the statistics of that season count it in `planned` and `total`, not in `ongoing` or `old` (`planned + ongoing + old + debt = total`). When its season comes it is an ordinary project, nothing is stored or moved. A project with a start later in the current season is not planned. Whether a project **has begun** is a matter of the day, while «planned» is a matter of the season: a project whose start day is still ahead cannot be created finished or with `isInTime` (400) and cannot be finished (409), inside the current season too (`isFutureDay`). `GET /projects/titles` leaves out the planned ones, and `TrackService.create` refuses a track for a planned one (409), because a track's season may not be in the future. A project that has tracks cannot be moved to a start in a season to come (409 «У проєкту вже є треки…», `ProjectsService.hasTracks`), because its tracks would stay in earlier seasons under a planned project; delete the tracks first. A project without tracks can be moved there in one edit, whether or not it has begun (a finished one must be reopened first, its end date cannot be before the start). A planned project can be moved anywhere in the window, including to today. The limit of two years is `shiftYears`, so 29 February of a leap year gives 1 March two years on. The date of a project launched from a proposal is whatever the form sends.
- A finished project has `isFinished`, `endDate` (not before the start, not in the future) and `isInTime`. `finish` sets them, `reopen` clears them, and `PUT` edits the end date and the flag only while the project is finished. `POST /projects` can create a project already finished (for backfilling old titles): an `endDate` with the same checks as `finish`, `isInTime` alone is refused. Progress (`episodesReleased`) is kept for a series and for a trailer, the «оповідки» (`EPISODE_TYPES`), and is 0 for a film or a short film. A track raises it for both (`markEpisodeReleased`). `backfill:episodes` catches up the trailers written before they had a count (see [setup.md](setup.md)). Participants are nickname text with roles, like tracks, and are not checked against the members list. There is no duplicate check on names.
- A project made from a proposal claims it first (`ProposalsService.markLaunched`, atomic, 409 when it is already a project) and the link lives on the proposal as `projectId`, never on the project. Deleting the project frees the proposal (`clearLaunched`). Any proposal can be launched, in an open or a closed season.
- A project has a poster, a link, an uploaded file or both, and `GET /projects` gives each one a ready `poster`. The upload, its processing and where the files live are in [posters.md](posters.md).
- A project may be a **collab**: `collabTeam` is the name of the team the project is made with (a string, at most 100 characters, trimmed). It is optional like `codeName`: an empty or blank value, or `null`, is not stored and is removed from a project on update (`splitOptionals`), so the project is a collab exactly when the field exists. The server stores nothing else about it (no flag, no list of teams); the page shows a «Колаба» badge from it. It changes no rule of seasons, tracks or finishing.

- There is one list of roles. Proposal paws and project participants take any `MEMBER_ROLE`, the same as tracks, and `MembersService.getAllRoles` (`GET /members/roles`) is the list with labels that the frontend shows everywhere, the proposals and projects pages included. A new role needs a label there (a spec checks that every `MEMBER_ROLE` has one). Every title is `isOngoing` or not, `funding` (`patron` or `order`) is an optional indicator that is only displayed, `isSequel` is a flag. Optional fields sent empty are removed, not stored blank.
