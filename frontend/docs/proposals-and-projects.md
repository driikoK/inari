# Proposals and Projects pages

Part of the frontend guide, see [CLAUDE.md](../CLAUDE.md).

## Proposals page

- `src/pages/Proposals/`: season tabs, a `ProposalCard` per title (participants grouped by role, every role of the list listed, a dash for an empty one), `JoinDialog`, and admin-only dialogs for seasons, titles and participants. Admin controls are gated by `SUBJECTS.MANAGE_PROPOSALS`, which only hides UI.
- The tab is remembered as soon as it is resolved. Deriving "the first open season" on every render makes the page jump to another season when the current one is closed.
- The quota «Ваша квота: n з 3» is only counted for display. The backend sends the limit (`maxPerPerson`) and refuses a join over it. A full member sees «Ліміт: n з n» on the other titles, and can still edit or withdraw where already joined.
- A closed season shows «Сезон закрито» in place of the join button. Deleting a season is offered only when it is closed.
- Curators (`MANAGE_PROJECTS`) get «Запустити проєкт» on a proposal that is not a project yet, which opens the project form pre-filled. A launched proposal shows a «Запущено» chip linking to `/projects?project=<id>` instead, and the proposals list is refetched after launching.

## Projects page

- `src/pages/Projects/`: season tabs (the server decides which seasons exist and flags the current one), a statistics row, a `ProjectTile` per project, and `ProjectCard` as a dialog. Curator-only: `ProjectFormDialog` (create, edit, and launch from a proposal), `FinishProjectDialog` and the delete confirmation, all gated by `SUBJECTS.MANAGE_PROJECTS`.
- Nothing about seasons, debts or statistics is computed in the browser. Each project in a season arrives with its `mark` (`ongoing`, `old` or `debt`) for that season, and the page only displays it. A project appears under every season it was on the layout of.
- On the current season's tab a finished tile is greyed, and disabled for a member. On a past tab nothing is greyed and every card opens.
- `ProjectFormDialog` loads the members first and mounts `ProjectForm` only after they are in, so a proposal's paws can be matched to nicknames (case-insensitive) when the form opens. An unmatched paw becomes an empty row that says «З пропозиції: …» and blocks saving until a nickname is picked or the row is removed. Rows carry a client-only `key`, which `toProjectPayload` drops.
- A **planned** project (a start in a season to come, up to two years ahead) arrives with `mark: planned` and gets a tab of its season after the current one, which the backend adds only when a season holds one, so nothing is listed by hand. The tile and the card show a «Заплановано» chip, the statistics of that tab get a «Заплановано» tile (only while it is more than 0), and the card has no «Завершено» while the start date is still ahead, even inside the current season (the backend would refuse it, 409). The track dialog does not list a planned project and its empty list says so. The start date of the form has `max` two years from today (`latestStartDay`, the same rule as `MAX_PLANNED_YEARS` on the backend) and the schema says the same. The count of released episodes is a field of the form and the «Прогрес» of the card for a series and for «Трейлери / оповідки» (`hasEpisodeCount`), always worded «Випущено серій».
- The team of a project is a list of rows in `ParticipantsEditor`, and the form validates on every change, so a row that has just been added would show «Оберіть нікнейм або видаліть рядок» and «Оберіть хоча б одну роль» before anybody touched it. The editor keeps which field of which row has been worked with (a choice, or leaving the field) and shows the error of that field only then. A try to save marks every row that is there at that moment (`submitCount`), and a row added after it starts clean again.
- The create form has a «Вже завершено» checkbox, for backfilling old titles, that reveals the end date and «Завершено вчасно». The edit form shows them only for a project that is already finished, and for a running one they come from the `FinishProjectDialog`. `isFinished` is a form value, not an argument of the schema factory.
- The poster of a project is two things in `ProjectForm`: `PosterField` (a file, uploaded after the project is saved) and the old text field with a link. The tile and the card show `project.poster`, which the backend fills with the uploaded file, else the link, so the page never chooses. Both show the poster whole (`object-fit: contain`, the free space has the colour of the placeholder), so a title written on a wide or square picture is not cut off. The box is `aspect-ratio: 0.7 / 1`, the shape of a MyAnimeList poster (the 23 links the team had measured 0.70 to 0.72), so those fill it to the edge. The placeholder of a tile with no poster has the same box, so the tiles of a row are equally tall. The field takes JPEG, PNG or WebP up to 5 MB (it checks before sending, the backend checks again), shows what was chosen at once from a local `blob:` address, and has «Скасувати вибір» for a file not sent yet and «Прибрати файл» for the one the project has. Nothing goes up until «Зберегти» or «Створити»: the project is written first, then `uploadPoster` or `deletePoster` (`createProject` gives the new id back for it). If the poster step fails the project is already saved, so the form closes and a toast says «Проєкт збережено, але постер не змінився», because keeping it open would make a second project on the next save. For the same reason the store keeps a write that went through when the list that follows it fails to load (`refreshAfterWrite` toasts the failure and goes on), so `createProject` always gives the id back.
- The card reuses `ParticipantsByRole` from the Proposals page, mapping `nickname` to `userName`. Both read the roles from `useRolesStore`.
